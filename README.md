# AegisOps

**Manufacturing: Intelligent Operations & Industrial Efficiency**

A Google-AI-grounded manufacturing reliability copilot with fleet replay,
historically trained anomaly models, topology correlation, traceable hypotheses,
review-only work orders, and human-approved sandbox verification.

- Live demo: https://aegis-ops-498775210896.asia-south1.run.app
- Source: https://github.com/puneetpahuja-eaton/aegisops-ai-builder-cup

## What is real, and what is simulated?

- Real: Gemini calls on Vertex AI, validated structured responses, historically
  trained detectors, topology correlation, tool events, quote validation, Cloud
  Storage reads, BigQuery audit writes, Cloud Run hosting and telemetry upload.
- Simulated: built-in assets, fault scenarios and SOPs. Uploaded measurements are
  replayed as provided and are never changed by sandbox approval.
- Not implemented: equipment control, production repairs, ticket dispatch,
  calibrated failure prediction, proven production savings.
- Confidence is a model's self-report, not a calibrated probability.
- This is incident triage / maintenance assistance, **not validated predictive maintenance**.

## Architecture

1. **Monitor** trains per-asset median/MAD, Isolation Forest and Mahalanobis
   diagnostics on healthy history. It scores each chronological fleet snapshot
   and tracks Markov event transitions and rolling fault-code rates.
   Robust-z >= 3 detects a deviation; Isolation Forest corroborates, not overrides.
   Mahalanobis is diagnostic only. Metric-only cases need two consecutive
   anomalous readings for the same metric; fault/unknown codes open immediately.
2. **Diagnostician** uses Gemini on Vertex AI with a Pydantic response schema.
   SOP IDs and numbered source-passage references must validate before a diagnosis
   is accepted; displayed quotes are copied from the SOP, not generated by Gemini.
   Upstream supply symptoms are grouped using topology and temporal coincidence.
   Independent local bearing, pressure, thermal and other faults remain separate.
3. **Decider** independently checks criticality, physical-repair codes, severe
   vibration, confidence, citations and a reversibility playbook. Critical or
   unknown-criticality downstream impact also escalates. The LLM cannot bypass this gate.
4. **Actuator** drafts a review-only work order, or awaits named human approval
   for a sandbox scenario. No command is sent to an asset.
5. **Verifier** uses subsequent replay snapshots, covering the root candidate
   and correlated symptoms. Two consecutive healthy snapshots are required within
   three ticks; continued faults fail/escalate and recurrence reopens the case.
   Uploaded recovery is observational, not proof of repair or savings.

Cloud Storage supplies versionable SOP and scenario files. BigQuery stores audit
events and supports a bounded seven-day operational-history query. Cloud Run
provides the application endpoint and service-account credentials.

These are five cooperating specialist agents in one shared session runtime, not
five independent LLMs. The shared state contains observations, rolling code memory,
training reports, tracked cases and timestamped named-tool events. Gemini
is essential for the diagnosis and escalation work-order drafting; numerical
evidence and review gates stay deterministic.

## Run the fleet demo

1. Open the live app and leave **Fleet operations** selected.
2. Select **Load built-in synthetic fleet** for a quick four-asset manufacturing
   demonstration, or **Load PRISM-style power fleet (22 assets / 6 scenarios)**.
3. Use **Process next timestamp** to step, or **Play replay**. Replay pauses when
   an approval or failed model analysis needs attention.
4. Watch actual model/tool updates as they execute. Inspect **Cases & approvals**,
   **Topology & models**, **Counterfactual**, and **Agent trace & audit**.
5. Enter a demo reviewer name for an eligible proposal and approve the sandbox.
   Process at least two later timestamps to verify. No real equipment is controlled.
6. Save case summaries to BigQuery if desired; download the full session audit.

The larger power demo covers voltage sag, overload, battery degradation,
temperature rise, harmonic distortion and breaker-open/downstream supply loss.
It trains on three synthetic days (864 readings per asset), then replays 96
five-minute snapshots. Known scenario labels are used only for post-hoc evaluation,
never passed to the reasoning agent or used to select an action.
Critical-asset policy is intentionally stricter than PRISM's original autonomous
demo: all actions here require named approval, and protected assets escalate.

### Replace sample data through the UI

Expand **Telemetry inputs, templates and privacy** and download the CSV or JSON
template. Replace its measurements and metadata with authorized non-confidential
data, upload it, and click **Load replacement telemetry**. Successful loading
replaces the entire previous fleet, history, models, replay cursor, cases and trace.
Invalid replacements show an error and leave the existing session unchanged.

CSV metadata columns:

```text
timestamp,asset_id,phase,asset_type,criticality,parent_id,event_codes,<numeric metrics...>
```

- `timestamp`: timezone-qualified ISO 8601.
- `phase`: `history` or `replay`. All history must precede every replay timestamp.
- At least 20 known-healthy history rows per asset; healthy codes are `OK`,
  `FAN_OK`, `SELFTEST_PASS` or `LOAD_HIGH`.
- `criticality`: `low`, `medium`, `high`, `critical` or `unknown`.
- `parent_id`: blank for a root; otherwise an existing asset ID. Cycles are rejected.
- `event_codes`: pipe-separated codes, such as `VOLT_SAG|TEMP_WARN`.
- Add up to 30 finite numeric metric columns. Features must be consistent per
  asset; blanks are allowed only for metrics not used by that asset throughout.
- Every replay timestamp must contain exactly one reading for every fleet asset.
- Maximum 2 MB per uploaded file, 50 assets, 20,000 total history rows and 10,000
  replay rows. Duplicate timestamps/assets, missing cells, unknown parents,
  nonfinite measurements and future-data leakage are rejected.

The JSON template has `assets`, `history`, and `telemetry` arrays. Each reading
contains `timestamp`, `asset_id`, `metrics` and `event_codes`. A user-supplied
`source: synthetic` cannot enable simulator mutation: uploads are always `uploaded`.

Uploading does not connect a PLC, SCADA, MQTT broker or sensor stream. "Real-time"
means live processing visibility during chronological replay. Uploaded data remains
in session memory unless you authorize Vertex AI processing or explicitly save
case summaries to BigQuery. Do not upload employer, personal or confidential data.
The currently configured SOP remains fictional and is not replaced by telemetry.
Unsupported conditions must be reviewed by a qualified engineer.

## Local setup

Python 3.11 is the deployment runtime.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
.\.venv\Scripts\python.exe -m streamlit run app.py
```

Select **Explicit offline simulation** to inspect the workflow without credentials.
Offline results are labeled and never presented as Gemini.

For Vertex AI, set:

```text
USE_VERTEX=1
GOOGLE_CLOUD_PROJECT=your-project
GOOGLE_CLOUD_LOCATION=global
GEMINI_MODEL=gemini-2.5-flash
```

Authenticate local application credentials with `gcloud auth application-default login`.
Alternatively, AI Studio requires `USE_VERTEX=0` and `GEMINI_API_KEY`.
The deployed Cloud Run service uses its attached service account, not a key.

If your corporate network intercepts TLS, use an approved trusted certificate
bundle; never disable TLS verification. This project supports the OS trust store.

## Tests and live verification

```powershell
python -m unittest discover -s tests -v
python -m cloud.smoke --all --audit
```

The live test requires Google application credentials or a short-lived
`GOOGLE_OAUTH_ACCESS_TOKEN` kept in process memory. Do not commit access tokens.
It verifies accepted Google AI diagnoses, approval, explicit verification,
Cloud Storage reads, BigQuery writes, and a history query.

The regression suite covers approval gating, model failure, bad citations,
wrong asset IDs, malformed types, unknown evidence, missing recovery readings,
reopened cases, storage failure, rejected audit rows, topology grouping, model
training without leakage, immutable uploaded data, all six power scenarios,
case deduplication, verification grace periods, retries and session isolation.

For a full browser check, with Streamlit running locally on port 8503:

```powershell
Set-Location submission
node .\verify-fleet.mjs
node .\verify-fleet.mjs --live
```

The live check uses only synthetic template data, calls real Vertex AI, saves a
case summary to BigQuery, replaces all asset IDs through the UI and checks that
approval cannot manufacture recovery in uploaded measurements.

## Deployment

`cloud/provision.py` creates dedicated build/runtime service accounts, a private
Cloud Storage bucket, and a partitioned BigQuery table with 30-day retention.
Its project/bucket defaults target this hackathon deployment; adjust them before
using another project.

```powershell
python -m cloud.provision
.\cloud\deploy.ps1
```

The Windows helper uses the locally installed Cloud SDK Python entrypoint.
For other environments, deploy the Dockerfile using `gcloud run deploy --source .`
with the same environment variables and service-account configuration.

Runtime permissions:

- Vertex AI User and BigQuery Job User on the project.
- Object Viewer on the **demo bucket only**.
- Writer on the **audit dataset only**.
- Dedicated build identity with Cloud Run Builder.

The runtime uses no embedded credentials. `.env`, tokens, certificates and local
logs are excluded from Git and cloud build uploads. Public source publication
must include only synthetic data, not employer materials.

## Failure semantics

- A Google AI failure shows an unavailable diagnosis and routes to human review.
  It is never silently replaced by an offline diagnosis.
- Invalid model output is rejected, not repaired into a success.
- Configured storage failures stop the run with an error.
- BigQuery row rejection is reported as failed persistence.
- Approval applies only to a sandbox, never to real equipment.
- SOP reference validation proves textual provenance, not industrial
  correctness or entailment of every generated sentence.

## Cost and deployment limits

The demo scales to zero, limits Cloud Run to one instance, and caps query bytes
at 10 MiB (BigQuery's minimum billed scan) for audit-history reads. This does **not** guarantee zero cost or impose
a project-wide spending cap. Vertex AI, builds, registry storage and regional
storage can incur charges. Set billing alerts and monitor public-demo usage.
Do not expose this prototype as an unrestricted production control system.
